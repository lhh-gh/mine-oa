> 项目代号：MineOA
> 技术基线：MineAdmin 3.2（Hyperf 3.x + Swoole，PHP 8.2+，**版本已锁定**）｜移动端：unibest
> 版本：v0.4（修订：合入 D5 复审意见；锁定 MineAdmin 3.2、移动端选型 unibest；**用户决策变更——OA 不采用插件化，改为主工程 App 层模块化**）

## 1. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端框架 | MineAdmin 3.2（Hyperf 3.x） | 自带 RBAC、菜单、日志、代码生成器；协程常驻内存，审批/打卡高并发友好 |

## 2. 分层架构与模块划分（主工程 App 层模块化，非插件）

**决策（2026-10-26 用户确认）：OA 不采用 MineAdmin 插件体系**，业务代码直接开发在
MineAdmin 3.2 主工程 `App/` 层内，以独立命名空间 `App\OA\...` 形成业务模块（对应 D5 第二轮 N1，
修订落点因用户决策变更而调整，见 D5 §3.4）。

> **非插件化的代价与对策**（必须在工程纪律中落实，否则升级 MineAdmin 时冲突面扩大）：
> 1. **OA 代码收敛在 `App/OA/` 独立目录**，禁止散落到 MineAdmin 原有目录；
> 2. **禁止修改 MineAdmin 主干文件**——确需扩展（如 PassportService 增加移动端登录、
>    菜单/权限 Seeder）时，优先用官方给的扩展点（继承/事件监听/配置覆盖），其次以
>    **最小 diff** 修改并在 Git 提交信息中标注 `[core-patch]`，升级时逐条复核；
> 3. **锁定 MineAdmin 3.2 版本**，升级决策单独评审（对比官方 diff 与本项目的 core-patch 清单）。

```
mineoa/                                   # 项目根（MineAdmin 3.2 主工程，OA 开发在其内）

│       ├── Http/

│       │   │   │   ├── Approval/         #   TemplateController（模板/单据类型配置）
│       │   │   │   ├── Attendance/       #   RuleController, ReportController

│       │   │       └── Approval/ Attendance/ Announcement/ Message/ Auth/

│       │   └── Request/                  # 参数校验（Vo/Request）
│       ├── Service/                      # 业务逻辑（事务边界在此）
│       ├── Repository/                   # 数据访问层
│       ├── Model/                        # 模型（oa_* 表 + 业务单据表）

│   └── src/interceptors/                 # 请求拦截（双 token）/ 登录拦截 / 路由拦截
├── migrations/oa/                        # oa_* 建表迁移（Hyperf 迁移目录内独立分组）
├── seeders/oa/                           # 种子数据（默认模板、菜单-权限点）
└── config/autoload/jwt.php               # 官方多场景 JWT 配置（scene 新增 mobile）
```

- 命名空间：`App\OA\...`（在 `composer.json` 的 psr-4 中注册 `"App\\OA\\": "App/OA/"`，
  实际注册方式以 3.2 源码 autoload 配置为准）。
- 权限点：管理端控制器使用官方注解 `#[Auth]` + `#[Permission("oa:approval:template:list")]`，
  权限标识随 `seeders/oa/` 写入菜单-权限表。
- **后台页面接入**（对应 D5 第二轮 N7）：OA 页面直接加入 MineAdmin 后台前端工程
  `web/src/views/oa/`（与主前端同一构建产物，无插件 web/ 加载环节），
  后台「菜单管理」配置菜单项指向页面组件路径（组件路径解析规则以锁定版本的前端
  源码为准，接入时先验证一个页面可挂菜单）。
- **请求流转**：HTTP(Swoole 协程) → Middleware(JWT/权限) → Controller → Service(事务边界)
  → Repository/Model/StateMachine → MySQL/Redis。
- 模块间只经 Service 接口调用，禁止跨模块直接操作他人 Model。

## 3. 关键流程

### 3.1 审批流转（核心链路）

```
发起人提交 → 创建审批实例(PENDING) + 业务单据(同事务) → 生成节点任务队列
  → 当前节点审批人收到待办(Outbox 事件 → 队列异步推送消息)
  → 审批人操作(同意/驳回/转交)
      ├─ 同意: 节点内全部处理 → 前进到下一节点 → 无下一节点则归档(APPROVED)
      ├─ 驳回: 按配置回退(发起人重新编辑 / 终止)
      └─ 转交: 任务处理人变更，节点不前进
→ 状态变更 + 操作留痕 + Outbox 事件写入(同一 DB 事务)
→ 后台投递任务消费事件(请假通过 → 考勤重算；推送待办消息)，消费端按事件 ID 幂等
```

**一致性与并发（修订，对应 D5 P0-2/P0-3/P0-4）**：

1. **实例为一致性边界**：状态变更、节点任务更新、操作日志、Outbox 事件五者同一事务。
2. **加锁顺序固定**：`instance → node → task`，分布式锁 Key 为
   `mineoa:approval:instance:{instanceId}`（不再只锁 task），防会签并发与"处理/撤回"并发。
3. **事务内二次校验**：锁内重读任务状态与节点完成性，条件更新（`WHERE id=? AND version=?`），
   失败路径明确返回 110002"任务已被处理"。
4. **Outbox 模式**：跨模块副作用（考勤联动、消息推送）一律先写 `oa_event_outbox`
   （同事务提交），由常驻投递任务扫描发送，消费端按 `event_id` 幂等——杜绝
   "DB 提交成功但进程退出导致考勤未更新/通知未发"。

### 3.2 移动端双端接入（H5 + 小程序）

**鉴权采用 MineAdmin 官方「多场景 JWT」方案**（官方文档：用户认证 → 为外部程序创建
单独的 JWT 生成规则；v3 基于双 token：access_token 短期 + refresh_token 刷新）：

```
1. 场景隔离：config/autoload/jwt.php 新增 mobile scene
   - 独立密钥 JWT_MOBILE_SECRET（.env 配置，与后台 JWT_SECRET 隔离）
   - ★ 显式配置更长 TTL（默认 access 1h/refresh 2h 面向后台，移动端建议
     access 12h + refresh 30d），并确认黑名单/单点登录策略
2. 专用中间件：仅做 JWT 校验 + 绑定当前用户
   ★ 不挂管理端 Permission/Operation 中间件——移动端是"员工身份 + 少量接口"，
     不需要每请求查询角色-菜单 RBAC
3. 用户体系：复用 MineAdmin user 表（以 user_type 字段区分用户类别，
   具体取值以锁定版本源码为准），不建独立的移动端用户表；
   管理类接口只从 admin/oa/* 入口暴露并走完整 RBAC（#[Auth]+#[Permission]）
4. 登录扩展：在 PassportService 中新增移动端登录方法（官方步骤）
```

**双端登录差异**（Token 结构与权限体系完全一致）：

```
  H5      → 账号密码 / 手机验证码（阿里云短信，60s 冷却、5min 有效）→ mobile scene JWT
  小程序  → wx.login 获取 code
            → 服务端 code2session 换 openid（AppSecret 只存服务端 .env）
            → 首次登录绑定员工账号（openid ↔ user_id 落库 + 手机验证码校验）
            → 签发同一 scene JWT
```

**安全要点**：身份一律以服务端 JWT 为准，禁止信任小程序端明文 openid/session_key；
`session_key` 不下发给前端。

**unibest 侧对接（新增）**：移动端工程模板为 unibest，对接方式——

- 请求封装：unibest 内置基于 `uni.request` 的请求拦截器，统一注入
  `Authorization: Bearer {access_token}`；后端双 token（access/refresh）下，401 时以
  refresh_token 换发新 token 并重放原请求（在拦截器中实现，并发请求等待同一次刷新）。
- 登录拦截：unibest 路由拦截器控制未登录跳转（白名单：登录页、公告只读页等）。
- 双端编译：`pnpm dev:h5` / `pnpm dev:mp-weixin`；构建 `pnpm build:h5` /
  `pnpm build:mp-weixin`（微信开发者工具导入 `dist/dev|build/mp-weixin`）。
- UI 库：wot-design-uni（Vant 不适配小程序端）。

**消息推送通道（修订）**：

- H5：**站内消息 + 角标**（浏览器 Web Push 移除——微信内置浏览器与国内浏览器环境
  不支持 Service Worker/推送服务，承诺不可兑现）。
- 小程序：审批待办产生时经 Outbox → 队列异步调用微信「订阅消息」；订阅消息为一次性
  授权，授权状态落库，未授权用户降级为站内消息 + 角标。AppSecret、模板 ID 走 `.env`。
- 紧急审批短信提醒：仅关键模板开关启用（成本高）。
- 企业微信应用消息：二期评估（受限于应用可见范围与频控，非"无限推送"）。

### 3.3 考勤打卡与日结

**打卡同步写库（修订，对应 D5 P0-2）**：打卡接口在事务内同步写入
`oa_attendance_record`（唯一键 `uk_user_date_type` 防重），提交成功才返回"打卡成功"；
推送/统计类副作用走 Outbox 异步。<500 人规模同步写库的峰值 QPS 有限（上班高峰
≤ 数百次/分钟），P95 < 500ms 由压测验证，无需异步写库引入的丢数据风险。

**日结**：Crontab 每日 00:30 对照排班生成考勤日记录；**日结可重算**（幂等设计）：
补卡生效、请假审批通过等事件触发对应日期重算。报表只查日结表，避免实时聚合。
展示口径分三段：**历史已结算 / 当日暂计（实时计算当天打卡）/ 未来未发生**——
未来日期为空是正常现象，不做"实时补齐后半月"。

**一期限定**：固定白班、单段工作时间、午休扣除（时长 = 跨午休部分减去午休时长）；
半天请假、跨日班次、多段班次不支持（二期演进）。

## 4. 自研审批状态机设计

用 PHP 8.1 **枚举 + 状态转移表**实现，纯内存计算、无外部依赖：

```php
<?php
// App/OA/StateMachine/ProcessStatus.php
// 审批实例状态枚举：所有合法状态集中定义，禁止魔法数字
enum ProcessStatus: int
{
    case DRAFT     = 1; // 草稿（发起人可撤回编辑）
    case PENDING   = 2; // 审批中
    case APPROVED  = 3; // 已通过（终态）
    case REJECTED  = 4; // 已驳回（终态或回退，按模板配置）
    case CANCELED  = 5; // 发起人撤回（终态）
}
```

```php
<?php
// App/OA/StateMachine/Transition.php
// 状态转移表：定义"当前状态 + 事件 => 目标状态"的全部合法路径
// 非法转移直接抛异常，保证流程不可被绕过（安全边界）
final class Transition
{
    /** @var array<string, ProcessStatus> key 格式: "当前状态:事件" */
    private const MAP = [
        'DRAFT:SUBMIT'     => ProcessStatus::PENDING,
        'DRAFT:CANCEL'     => ProcessStatus::CANCELED,
        'PENDING:APPROVE_ALL'  => ProcessStatus::APPROVED,   // 当前节点全部通过且为末节点
        'PENDING:REJECT_TO_START' => ProcessStatus::DRAFT,   // 驳回至发起人（可重新编辑）
        'PENDING:REJECT_END'    => ProcessStatus::REJECTED,  // 驳回终止
        'PENDING:CANCEL'    => ProcessStatus::CANCELED,      // 首个节点未处理前可撤回
    ];

    public static function go(ProcessStatus $from, string $event): ProcessStatus
    {
        return self::MAP["{$from->name}:{$event}"]
            ?? throw new \DomainException("非法状态转移: {$from->name} + {$event}");
    }
}
```

**节点层状态**（实例内）：`WAIT(未到) → ACTIVE(当前待办) → PASSED/REJECTED(已处理)`。
一期为**顺序审批**；会签（并行节点 = 节点内多任务全部 PASSED 才前进）随三阶段落地，
其并发正确性依赖 §3.1 的实例级锁序与事务内二次校验。

### 4.1 状态机边界规则清单（修订，对应 D5 P1-1）

| # | 边界场景 | 风险 | 实现策略（修订后） |
| --- | --- | --- | --- |
| B1 | **审批人动态解析**：`dept_leader` 型节点发起时解析部门负责人 | 负责人离职/空缺 → 流程卡死 | 解析链：①复用 MineAdmin `dept_leader` 关联（部门 N:N 负责人）②空缺时上溯上级部门负责人 ③仍未命中→**阻止提交**（返回 110003"未找到可用审批人"）；模板可配置**业务兜底审批人**（指定角色/人员，非超管——技术超管不应默认拥有业务审批权） |
| B2 | **节点超时**：有人长期不处理 | 流程永久挂起 | Crontab 每日扫描 ACTIVE 超 N 天（默认 7 天，按模板可配）的节点发提醒；超 30 天升级提醒其上级；不做"超时自动通过"（默认关闭，可按模板开启） |
| B3 | **驳回后的回退实现** | 任务重建语义不明确会破坏留痕 | 作废**仅限未处理任务**（status=4 自动作废），已处理任务与 log 全保留；全部节点重置 WAIT，从 seq=1 重新激活，**轮次 round+1**；log 追加 action=6 重新提交 |
| B4 | **审批人自审批**：发起人即审批人 | 单节点流程自我循环、绕过内控 | 默认**转交上级/模板配置的替代审批人**处理；auto-pass（自动跳过）作为模板级可配置项**默认关闭**；启用时生成独立 log action=8"系统自动跳过" |
| B5 | **转交死循环**：A 转给 B、B 转回 A | 任务空转 | 同一任务链内转交目标不得出现在本任务历史处理人链中（110005） |
| B6 | **审批中组织变更**：人员调动、模板停用 | 在途实例行为不确定 | 实例化快照已隔离模板变更（含表单定义快照与模板版本，D3 §1.2）；人员调动不影响已实例化任务；仅 B1 解析链实时查组织架构 |

> 编码验收标准：B1–B6 在单元测试中各有至少 1 个用例（D6 验证脚本覆盖）。

## 5. 高并发决策（中小规模够用 + 留扩展位）

| 场景 | 策略 |
| --- | --- |
| 早高峰打卡 | **同步事务写 MySQL**（唯一键防重），提交成功才返回；推送/统计走 Outbox 异步（D5 P0-2 修订） |
| 部门树/权限 | Redis 缓存，TTL 5min + 修改后台主动失效 |
| 审批待办列表 | 待办数走 Redis 计数器，列表查库 |
| 审批待办推送 | Outbox → 队列异步推送（小程序订阅消息 / 站内消息），推送失败不阻塞主流程 |
| 报表导出 | 大数据量报表队列生成文件 + 站内信通知下载链接 |
| 缓存防护 | Key 规范 `mineoa:{module}:{biz}:{id}`；TTL 加随机抖动防雪崩 |

## 6. 可观测性、错误处理与数据权限（前置设计）

### 6.1 统一响应与异常

沿用 MineAdmin `Result` 结构；业务异常抛官方异常类（统一错误码规范
`1000 + 模块号*100 + 序号`），全局异常处理器统一捕获，禁止堆栈外泄。

### 6.2 结构化日志与指标

- PSR-3（Hyperf `Logger`），审批关键操作记录 `trace_id + user_id + instance_id + 耗时`，
  按 `oa/approval` 通道独立文件。
- 指标：审批流转 P95 耗时、**Outbox 积压长度**（新增）、队列堆积、打卡接口错误率。
- 告警：日结任务失败、**Outbox 投递失败超阈值**、队列堆积超阈值 → 管理端站内信 + 邮件。

### 6.3 Swoole 常驻内存工程约束（新增，对应 D5 第二轮 N6）

- **发布需重启**：常驻内存无 PHP-FPM 式"传完即生效"，发布走平滑重启
  （`kill -USR1`/容器重启，pid 见 `runtime/hyperf.pid`）；开发期用 `server:watch` 热重载。
- **静态状态污染**：禁止在 Service/Controller 写静态属性、单例可变状态——跨请求共享会
  串数据；需要请求级状态一律走协程上下文。
- **禁用阻塞调用**：`exit/die`、`sleep`、同步 curl 会阻塞整个 Worker。
- **CurrentUser 作用域**：只在 HTTP 请求周期可用；Service 层不注入，队列消费者/Crontab
  中不可用（官方文档明确）——用户身份作为参数传入。
- **连接池**：MySQL/Redis 连接池按 Worker 数配置（4C8G 建议 pool ≤ 64），压测校准。
- **内存监控**：Worker 内存埋点（`memory_get_usage` 周期上报），长跑泄漏可告警。

### 6.4 数据权限对接（新增，对应 D5 第二轮 N3）

MineAdmin 3.x 数据权限通过 `#[DataScope]` 注解（`deptColumn` / `createdByColumn` /
`scopeType` / `onlyTables`）+ 策略类型（DEPT_SELF/DEPT_TREE/SELF/ALL/CUSTOM_DEPT/CUSTOM_FUNC）实现：

- **列映射**：OA 表使用业务语义列名，接入时显式声明映射——
  `oa_approval_instance`：`deptColumn='origin_dept_id'`、`createdByColumn='origin_user_id'`；
  `oa_attendance_day`：`deptColumn` 需联表或冗余 `dept_id` 列（以锁定版本实现为准）。
- **协程上下文隔离（官方严重警告）**：数据权限上下文必须在请求协程内设置；
  自建协程（队列消费、并行处理）中执行带数据权限的查询前，必须先在该协程内重建
  用户上下文，否则会发生"A 用户看到 B 用户数据"的越权泄露。
- HR 报表类接口默认挂 `DEPT_TREE` 策略（部门及子部门），超管 `ALL`。
- 接入完成后以"普通员工查 HR 报表被拦截"作为专项测试用例（D1 验收 5）。

## 7. 部署拓扑（单机起步）

```
Nginx(HTTPS, 静态资源/反代)
  ├── /admin        → MineAdmin 后台前端构建产物（OA 页面在主前端工程内一并构建）
  ├── /h5           → uni-app H5 构建产物（静态）
  └── /api          → MineAdmin(Hyperf, Swoole 多进程) ── MySQL 8.0
       /api         ← uni-app 小程序端直连（HTTPS 强制，微信平台硬性要求）
                                                └── Redis 6
                    └── Crontab 进程（考勤日结/Outbox 投递/公告定时）
Docker Compose 一键起：php+swoole / mysql / redis /（三阶段可选 libreoffice）
备份：mysqldump 每日全量 → 保留 7 天
```

**小程序发布链路**：微信后台配置合法域名 → 开发者工具上传 → 提交审核（企业主体）；
AppSecret / 订阅消息模板 ID / 短信 AccessKey 通过 `.env` 注入，**禁止明文写入代码与前端构建产物**。

**短信报备**：企业签名 + 验证码/通知模板提前 1~2 工作日报备（阻塞项，立项即办）。

环境要求：服务器 4C8G 起步；`.env` 管理 DB/Redis/JWT 密钥/微信凭据/短信凭据，**禁止明文入库**。
