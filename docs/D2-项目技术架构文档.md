# MineAdmin OA 系统 — 项目技术架构文档（D2）

> 项目代号：MineOA
> 基线：MineAdmin 3.2（组件 v3.2.0，以 composer.lock 为准），web 3.2.1，unibest 4.4.1
> 版本：v0.5｜日期：2026-10-26｜按 D9 A01–A16 统一设计；本文中的新增组件均待实现

## 1. 技术选型与范围

| 后端 | PHP 8.2+、Hyperf 3.2、Swoole 5.1+、MineAdmin 3.2 | 主工程按层模块化，不采用插件 |

命名空间严格遵循目录；`App\` 已映射 app，无需新增 autoload。`Exception` 为单数。
Controller 负责验证与 DTO/Result，Service 编排业务和事务，Repository 负责查询与条件更新，Model 映射表。
业务域之间经 Service 接口调用；身份以可信 Actor 参数传递，后台任务不读取 HTTP CurrentUser。
OA 文件集中在各层 OA 子目录；框架必需扩展列入 §8 core-patch 清单。

迁移与种子采用现有 databases 根目录：MineAdmin 注册该路径，Hyperf 扫描不递归。
新增文件必须纳入 migrate:status、首次安装、增量升级的核对清单。不得再建立未注册的 migrations/oa 子目录。

## 3. 控制器、响应与错误码

Admin 控制器沿用 `App\Http\Admin\Controller\AbstractController`；类级使用
`#[HyperfServer(name: 'http')]` 和 AccessTokenMiddleware / PermissionMiddleware / OperationMiddleware
（优先级 100/99/98）。方法使用 Swagger `Get/Post/Put/...` 的完整路径，以及
`#[Permission(code: 'oa:approval:template:list')]`。所有写接口配对应 Request::validated()。
Api 同样使用 HyperfServer 和完整路径，认证端点与业务端点分开挂中间件；不照搬不存在的 Auth 注解。

唯一前缀：管理接口 `/admin/oa/*`，移动认证 `/api/v1/oa/auth/*`，移动业务 `/api/v1/oa/*`。
用户信息和后台登录保留 `/admin/passport/*`。接口明细、权限点和分页以 D4 为唯一契约。

统一返回 `{code,message,data}`。**选定受控扩展官方 `App\Http\Common\ResultCode` 枚举**，
增加 100xxx（认证）、110xxx（审批）、120xxx（考勤）、130xxx（文档）、140xxx（投递/导出）命名 case；
每个 case 的六位值以 D4 表为准，不再用算式推导。业务异常统一使用 `App\Exception\BusinessException`，
或 OA 子类；不得将独立枚举直接传入强类型 ResultCode 参数。每次抛错提供可读 message，并补翻译。

沿用当前响应兼容策略：应用处理后的业务响应 HTTP 200、JSON code=200 为成功；
认证失败 JSON code=401，权限失败 403，参数失败 422；OA 业务拒绝用六位码。
网关/基础设施仍可产生非 2xx HTTP 状态，前端分别处理 HTTP 状态和业务码；任何六位业务码不作为 HTTP 状态。
生产关闭调试堆栈。分页统一 `page/page_size`，返回 `data:{list,total}`，page_size 上限100。

## 4. 员工身份与双 token

### 4.1 同一用户、多种角色、独立终端场景

内部员工复用 `Type::SYSTEM`（100），基础角色 `oa_employee`；审批人、HR、模板管理员是附加角色。
SYSTEM 不等于超管，不授予员工系统管理权限；USER(200) 保留外部类别。PC 继续使用现有后台登录、default JWT。
移动登录查询同一个 SYSTEM 员工，要求账号有效且具有 oa_employee 资格；签发 mobile JWT。
已存在的 USER 员工数据须单独形成映射/合并清单，不自动批量转型。

### 4.2 配置位置与认证组件

以已安装 `vendor/mineadmin/jwt/Factory.php` 为准：Factory 读取 `jwt.default` 和 `jwt.mobile`，
**mobile 位于 jwt.php 返回数组顶层，与 default 同级**。在现有 default 配置外新增以下片段：

```php
'mobile' => [
    'key' => \Lcobucci\JWT\Signer\Key\InMemory::base64Encoded(env('JWT_MOBILE_SECRET')),
    'ttl' => (int) env('JWT_MOBILE_TTL', 43200),
    'refresh_ttl' => (int) env('JWT_MOBILE_REFRESH_TTL', 2592000),
    'blacklist' => [
        'enable' => true,
        'prefix' => 'mineoa_mobile_jwt_blacklist',
        'connection' => 'default',
        'ttl' => (int) env('JWT_MOBILE_BLACKLIST_TTL', 2592001),
    ],
],
```

密钥、黑名单命名空间与后台分离，其余配置从 default 合并。`get('api')` 调用存在不代表已有独立 api 配置。
新增 MobileAuthService，组合 UserRepository 与 Factory->get('mobile')；不继承 final PassportService，
不修改其私有场景字段，也不改全局 CheckTokenInterface 绑定影响后台。
MobileAccess/RefreshMiddleware 显式注入 mobile 的签名校验、黑名单检查及员工有效性检查；
签发、校验、刷新和退出全过程使用同一 mobile 场景，刷新专用中间件解析 refresh token。
Mobile AuthController 不调用 CurrentUser::refresh()，因为该方法指向默认 PassportService。

PC 通过现有 CurrentUser 取得用户；移动中间件将已验证身份写入请求/协程上下文并加载用户，构造可信 Actor。
业务 Service 只接收 Actor，不从客户端接收 origin_user_id 或用户类型作为身份依据。

### 4.3 生命周期及绑定

D4 固定登录/刷新响应：access_token、refresh_token、access_expires_in、refresh_expires_in（均为剩余秒数）。
mobile API 层映射为现有 useTokenStore 的驼峰 DTO；useUserStore 只存资料。
`VITE_AUTH_MODE=double`；统一刷新协调器只发一次刷新，后续请求等待；刷新请求不进入自身重放队列，
失败时拒绝全部等待请求、清理本地身份并回登录；每个原请求最多重放一次。
签发回调加入随机 sid 与 rotation，保持框架用户ID claim 不变；刷新时 rotation+1，旧 token 对失效。
会话硬寿命为首次登录后30天，响应有效秒数取配置TTL与剩余会话寿命的较小值。logout 以 refresh token 注销该会话并使其关联 access 失效，
由 mobile 专用会话记录 `oa_auth_session` 支撑关联与撤销，详见 D3 §5.5。

微信未绑定时返回短期一次性 bind_ticket，不返回员工 token；绑定必须校验已有员工及短信验证码。
服务端完成 code2session，不接收前端 openid 作为身份凭证；session_key 不下发。
所有公告为内部内容，公告页也要求登录；前端白名单只有登录、绑定和必要的错误页。

## 5. 审批、一致性与可靠副作用

### 5.1 实例事务边界

创建前在事务内核对发起请求的templateVersion并冻结模板；版本变化要求前端重新确认。
创建审批实例、业务单据、轮次快照、节点、任务、抄送关系、审批日志、Outbox 及消费目标在同一事务提交。
状态变化固定按 instance → node → task 加数据库行锁，version 条件更新作为二次校验；
Redis 实例锁仅用于降低争用，不替代数据库正确性。锁超时明确失败，释放时校验持有者。
发起请求携带 client_request_id，以用户+请求号唯一约束保证网络重试不重复创建实例。
一阶段请假时长使用 `config/autoload/oa.php` 中带版本的固定工作日历：周一至周五9–18点、午休12–13点及显式日期例外；
默认整工作日粒度，发布前按企业制度配置并冻结到单据 calculation_snapshot，不依赖二阶段考勤规则表。
二阶段按日期接入不可变规则版本，新单据冻结新依据，既有已批单据不因规则管理上线而静默改时长。
请假重叠检查在员工级串行事务内进行；以稳定的用户行/专用员工互斥记录锁定，避免并发创建不同实例时穿透。

实例状态：DRAFT(1)、PENDING(2)、APPROVED(3)、REJECTED(4)、CANCELED(5)。合法转移：
DRAFT+SUBMIT→PENDING；PENDING+APPROVE_ALL→APPROVED；PENDING+REJECT_TO_START→DRAFT；
PENDING+REJECT_END→REJECTED；DRAFT/PENDING+CANCEL→CANCELED（PENDING 仅首节点尚无人操作时）。
REJECTED 为终态，只能另建新实例，不提供原实例重提。

| 规则 | 决策 |
| --- | --- |
| B1 审批人 | 主部门负责人→上溯部门→模板业务兜底；仍无可用员工则拒绝提交，不默认转超管 |
| B2 超时 | 活动节点超过7天提醒，30天升级；不自动通过，模板可配置提醒阈值 |
| B3 驳回重提 | 回退到 DRAFT 时关闭当前轮次、作废未处理任务；resubmit 才 round+1，追加新轮次与节点，不重置旧节点 |
| B4 自审批 | 转上级/替代人；默认不自动跳过；后续允许 auto-pass 时独立记录 action=8 |
| B5 转交 | 转交目标不在当前任务链历史人集合，保留 parent_task_id/chain_id，不前进节点 |
| B6 组织变化 | 发起时冻结主部门、审批人、表单定义与业务值；重提复用冻结模板规则，人员有效性重新检查并保存新轮次解析结果 |

一阶段每个顺序节点解析为唯一处理人；部门/角色命中多人则要求管理员改为显式单人节点，
无法唯一确定则拒绝提交，不能暗中变成会签。三阶段会签仅全员通过前进，不引入未定义 pass_ratio。
抄送按模板+合法自选接收人计算后冻结在 oa_approval_cc；详情支持按 round 读取不可变历史。
模板 JSON 配置仅为有限字段/顺序节点编辑，拖拽表单设计器与 BPMN 不在首期。

### 5.2 MySQL 持久化投递与消费确认

首期采用 **MySQL 直接领取和消费**：Outbox 事件与每个目标消费者的 oa_event_delivery 同事务写入；
Redis 仅缓存或可选唤醒，丢失后可从数据库恢复。事件生产事务为每种事件展开固定消费者名单，
不会因为一个消费者完成就删除其余消费者的任务。

1. 消费进程领取 status=READY 且 next_retry_at<=now 的任务，设置 PROCESSING、owner_token、lease_until。
2. 内部数据库副作用在事务内锁 delivery，校验当前领取者；执行副作用并将 delivery 置 DONE 同事务提交。
3. delivery 的 (event_id,consumer) 唯一键是持久化收据；消息另有事件+接收人唯一约束。完成收据保留至审计保留期结束。
4. 崩溃后 lease 到期可再领取；未提交副作用回滚，已提交 DONE 不再执行。失去租约的旧执行者不能提交完成。
5. 初次失败后最多重试3次，间隔1/5/30分钟，总尝试4次；再失败置 DEAD，告警并允许人工有痕重投。
6. 所有目标 delivery DONE 后事件记 PROCESSED；存在 DEAD 记 NEEDS_ATTENTION。不存在“入 Redis 即业务完成”的 delivered 状态。

事件路由固定为：approval.task_created→message.create；approval.finished→message.create（第二阶段新增attendance.recalculate）；
attendance.corrected→attendance.recalculate；report.export_requested→report.export；message.push→wechat.send（第三阶段）。
当前阶段尚未交付的消费者不注册；第二阶段日结初始化从已批准请假事实计算历史，不假设旧事件自动拥有新目标。

外部微信/短信无法与数据库原子提交：使用独立推送记录和业务去重键；结果不明确标 UNKNOWN，
按服务商幂等/查询能力处理，不宣称 exactly-once，不盲目重复发送。站内消息不依赖外部推送成功。
长任务定期续租并以 owner_token 条件更新；清理不得删除尚未确认或死信事件。指标包含 READY 积压、最老事件年龄、DEAD、租约超时和 UNKNOWN。

## 6. 考勤与数据权限

### 6.1 考勤历史

二阶段固定白班、单段时间、午休扣除；前三阶段不支持半天粒度请假。起止日期可跨多个完整工作日，
按每一天生效规则累计时长；固定分钟口径计算后展示小时，禁止客户端提交时长作为事实值。
打卡同步事务写原始表，唯一键(user_id,work_date,type)，只追加；work_date 按 Asia/Shanghai 当地日期。
补卡保留审批通过的修正记录，不插入或覆盖原始打卡；重算叠加最新有效修正并记录来源。

规则内容版本不可变，部门适用关系为关联表，区间 [effective_from,effective_to)，同部门不得重叠。
默认规则的部门标识0；先精确主部门匹配，再取默认；不自动继承上级部门规则。允许打卡窗口为规则punch_open/punch_close，不跨日；非工作日可记录卡，但不自动计作工作日出勤。
办公主部门由 oa_employee_department 按工作日查询，历史版本保留；不以重算当天的部门替代历史归属。
首次日结冻结 dept_id、rule_id，正常重算沿用快照；纠错迁移必须单独授权、留痕并记录前后值。
月报查日结；当天暂计、历史已结算、未来未发生明确区分。

### 6.2 功能权限、数据范围、资源归属

Admin 挂 RBAC 中间件；移动挂员工身份与资源授权；所有业务 Service 都校验任务/申请/公告/目录归属。
模板可发起范围与抄送/转交选择范围在服务端校验。部门范围为空、员工无有效策略或主部门缺失时，
普通员工相关查询返回空/拒绝，不能依赖框架默认“无策略则放行”。超管仅按明确后台授权查看，不自动取得业务审批任务。

| 查询 | onlyTables | 列映射/ScopeType | 授权策略 |
| --- | --- | --- | --- |
| 审批部门管理列表 | ['oa_approval_instance'] | origin_dept_id/origin_user_id；ScopeType::DEPT | PolicyType::DeptTree，按用户有效策略配置 |
| 考勤报表 | ['oa_attendance_day'] | dept_id/user_id；ScopeType::DEPT | HR 的 DeptTree，明确授权者可 All |
| 个人申请/待办/抄送 | 显式业务条件 | 当前 Actor 的 origin_user_id、task.user_id 或 cc.user_id | 不以部门范围替代参与者归属 |
| 公告与私有文档 | 显式业务授权 | 指定部门/目录 view/upload/manage | 不沿用个人列表规则 |

DataScope 的 scopeType 使用 `App\Library\DataPermission\ScopeType`；部门树属于
`App\Model\Enums\DataPermission\PolicyType::DeptTree`，不是 scopeType 枚举值。
Controller 在进入注解服务前加载 CurrentUser::user()；onlyTables 必须明确，复杂联表和别名查询显式施加数据条件。
授权服务先计算允许集合并处理空集合，再结合 DataScope；角色/策略变更失效相关缓存，私有下载与导出执行时回源核对有效授权，不能仅依赖旧用户缓存；策略种子与用户有效策略分配一起交付。
异步导出保存可信 operator_id 和申请时部门集合，执行前重新检查账号与权限，取申请范围和当前范围交集；产物记录实际包含的部门集合，下载时若范围已收缩则拒绝旧文件并要求重新生成；
在消费者内以显式查询范围执行，不读取 HTTP CurrentUser，也不直接信任前端 deptId。

## 7. 文件与运行约束

OA 附件使用新增 private_oa 存储配置、attachment 元数据及 oa_attachment 私有归属映射；
上传由OA专用服务完成，attachment.url不填裸URL；OA映射记录物理对象键、上传者、用途及业务归属，
公共附件入口不得将这些对象按公开附件处理。文件不位于公开 /uploads 映射下，
不向浏览器返回可长期直达的物理 URL。通过业务文件 ID 每次认证授权后流式下载，不返回裸存储 URL；后续如采用签名交付须另行设计撤销与过期语义。
预览 PDF 使用相同私有策略；没有转换结果时返回明确未就绪状态。单据私有附件一阶段即启用；原生 PDF 三阶段可用，Office 转换后续启用。
请假附件与目录附件均校验上传者、用途和业务关联；未关联私有附件有过期清理策略。

请求状态使用协程上下文，禁止单例可变用户/场景状态；队列/Crontab 只接受可信 Actor 或系统任务范围。
连接池按总进程数校准，文件转换及长耗时外部调用放后台进程，设置超时。
生产更改代码或配置使用完整应用进程重启/容器重新创建；Worker reload 不等价于重载全部用户进程和启动配置。
日志含 trace_id/user_id/instance_id/event_id/consumer/耗时，凭据不入日志；对外无堆栈。

## 9. 部署与交付

部署固定独立主机名：`admin.example.com/` 为 PC 静态，`m.example.com/` 为 H5 静态，

小程序合法域名配置 `https://api.example.com`，不含路径。具体 Nginx、构建与回滚见 D7。
性能 P95、权限有效性、可靠投递和两端兼容性均须实现后验收，D5/D6 跟踪，不提前关闭。
