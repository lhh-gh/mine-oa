# MineAdmin OA 系统 — 设计复审报告

> 评审对象：D1《用户需求梳理》v0.1 / D2《项目技术架构》v0.1 / D3《数据字典》v0.1 / D4《API 接口文档》v0.1
> 评审日期：2026-10-26 ｜ 结论：**选型保留，文档定稿前需完成一轮统一修订**
> 状态跟踪：[ ] 待修订 → [x] 已修订

---

## 1. 总体结论

1. **MineAdmin 3.x 选型成立**：内置 RBAC / 部门 / 附件 / 操作日志与 OA 高度重合；
   基于 Hyperf，协程、队列、Crontab 齐备；社区已有 H5/小程序多场景接入实践。
2. **架构方向成立**：单体模块化（<500 人）、自研有限审批状态机、uni-app 双端，
   四项核心决策均无推翻必要。
3. **主要风险不在选型，而在设计完整性**：权限、可靠性、业务建模三类缺口，
   以及两轮修订后产生的文档间不一致。D1–D4 目前是**待统一修订的初稿**，
   不应直接作为编码基线。

## 2. 问题清单（按严重程度）

### P0 — 数据可信 / 业务一致性（编码前必须解决）

| # | 问题 | 现状证据 | 修订要求 |
| --- | --- | --- | --- |
| P0-1 | **移动端权限过度简化**：D2 §3.2 写"员工全量可访问移动端功能" | 登录 ≠ 授权：模板发起范围、任务归属、附件下载、他人申请可见性均需授权规则 | 统一员工身份；按功能授权（模板可发起范围）+ 资源授权（任务归属校验）+ 业务动作留痕；离职/停用/解绑后的 Token 失效策略 |
| P0-2 | **打卡"异步落库即返成功"不可靠** | D2 §5 / D4 §3：Redis 入队后即返 success，队列故障 → 前端成功、库里无记录 | 一期改为**同步事务写 MySQL，提交成功才返回**；通知/统计异步；性能靠压测验证（<500 人规模本不需要异步写库） |
| P0-3 | **审批并发锁粒度不足**：只锁单 task，未覆盖实例级竞争 | 会签节点两人同时同意/一人同意一人驳回；处理与撤回并发 | 以**实例为一致性边界**：固定加锁顺序（instance→node→task），事务内二次校验任务状态与节点完成性；明确乐观锁条件更新失败的处理路径；Redis 锁仅作辅助 |
| P0-4 | **DB 提交与队列发布脱节** | 审批事务提交成功、进程退出 → 考勤未更新、通知未发 | 同事务写业务结果 + **Outbox 事件表**，后台任务可靠投递，消费端按事件 ID 幂等 |
| P0-5 | **审批历史不可完整还原** | 节点有快照，但表单定义仍引用当前模板（D3 §1.2 实例仅 template_id + form_data） | 实例化时**冻结表单字段定义**（定义快照或模板版本号）；记录**审批轮次**；作废旧任务仅限"未处理"任务，已处理记录全保留 |

### P1 — 规则冲突 / 业务建模（修订文档时解决）

| # | 问题 | 修订要求 |
| --- | --- | --- |
| P1-1 | **D2 §4.1 B1–B6 边界规则自身冲突**：①B1 同时写"转超管兜底"与"不允许提交"矛盾，且技术超管不应默认拥有业务审批权；②自审批 auto-pass 可能绕过内控；③"自动跳过"复用 action=7 自动作废语义错误 | B1 统一为：**无可用审批人 → 阻止提交**，或转模板配置的业务兜底审批人（非超管）；自审批默认**转上级/替代审批人**，auto-pass 作为可配置项；新增独立 action"系统自动跳过" |
| P1-2 | **通用表单替代不了业务单据**：请假/报销/采购/用章均为一期核心，但仅设计了通用审批表 | 采用**业务单据表 + 通用审批实例**双层：请假表（假别/起止/时长/重叠检查）、报销表（金额明细/票据）、采购表、用章表各自落业务列；JSON 表单仅承载附加说明字段。上一轮"字段定义一律行化"修正过度，撤回：字段定义可保留版本化 JSON，**固定查询字段落业务列建索引** |
| P1-3 | **考勤模型表达能力不足**：半天请假、多段请假、跨日班次、多次打卡均不支持 | 一期明确限定：固定白班 + 单段工作时间 + 午休扣除；原始打卡只记事实、日结可重算；补卡单独留痕；考勤规则增加**生效日期**；展示口径分"历史已结算 / 当日暂计 / 未来未发生"——未来日期为空是正常现象（撤回上一轮"实时计算补齐后半月"的修正理由） |
| P1-4 | **文档间不一致**：①D1 非目标写"会签后续演进"，D2 一期支持会签；②撤回条件 D1"下一节点未处理前"与 D2"首节点未处理前"不一致；③D4 审批示例 action=2（驳回）意见却是"同意"；④D4 文档中心只有 /admin 接口，与 D1"H5 可用文档中心"矛盾；⑤D4 未随 D3（template_field 行化）同步修订 | 逐项统一：会签归入**二期**（一期顺序审批即可闭环）；撤回条件统一为"首个节点未处理前"；示例意见改为"同意放行"；补 H5 文档中心只读接口；D4 全量对齐 D3 |
| P1-5 | **过度承诺**：企业微信"无限推送"、站内消息"必然可达" | 改为相对表述：企业微信受限于应用可见范围与频控；站内消息为默认保底通道 |

## 3. 修订后的分期交付计划

| 阶段 | 范围 | 核心验收 |
| --- | --- | --- |
| **一阶段** | 员工登录（三端）、权限基线、固定请假表单、顺序审批、站内消息 | 完整走通一次请假；越权与重复提交被正确拦截 |
| **二阶段** | 固定白班打卡、补卡、请假-考勤联动（Outbox）、考勤月报 | 审批结果可靠影响考勤；补卡后可重算 |
| **三阶段** | 会签、公告、文档权限、报销/采购/用章业务单据 | 并发会签正确；业务单据权限完整 |
| **后续** | 可视化流程配置、复杂排班、Office 预览、企业微信通道 | 按需独立验收 |

> 关键决策：**会签从一期移除**。顺序审批即可验证状态机、事务、Outbox 全链路；
> 会签引入的实例级并发复杂度（P0-3）在二阶段有测试基建后再落地。

## 4. 保留项（评审确认无需改动）

- MineAdmin 3.x 选型、单体模块化、自研有限状态机、uni-app 双端
- 模板/实例分离 + 节点快照（D3 §1.1/1.3）
- 实例/任务乐观锁字段（D3 §1.2/1.4）
- 复用 MineAdmin `dept_leader` / `user.type`（不平行建组织数据）
- 审批日志只追加、打卡原始记录只追加
- 官方 JWT 多场景方案方向（细节以锁定版本源码为准）
