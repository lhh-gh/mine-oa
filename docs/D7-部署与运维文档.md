# MineAdmin OA 系统 — 部署与运维文档（D7）

> 版本：v0.5｜日期：2026-10-26｜对应D9 A01/A07/A08/A10/A11/A15/A16
> 状态：生产部署设计；生产Compose/镜像、oa:seed、oa:smoke、/health及OA消费进程均待实现

## 1. 环境与现状

| 项 | 要求 |
| --- | --- |
| 服务端 | Linux，PHP8.2+、Swoole5.1+，扩展按composer.lock校验；初始4C8G，按内存/连接池实测调整 |
| 数据库 | MySQL8.0、InnoDB、utf8mb4；历史数据和命名卷持久化 |
| 缓存 | Redis6+，建议生产Redis7.2，AOF开启；不存未确认事件的唯一副本 |
| 构建 | Node22 LTS≥22.12.0，pnpm10.10.0，两端分别使用冻结lockfile |
| 网络 | admin/m/api三个HTTPS域名；仅Nginx对外开放，MySQL/Redis/9501内网 |
| 存储 | 数据库、private_oa附件、备份、日志分别有持久目录与容量告警 |

当前仓库docker-compose.yml仍使用PHP8.1/MySQL5.7且hyperf服务tail保持空闲，
deploy.test.yml同样为旧PHP镜像；它们不满足本设计，不能直接宣称生产就绪。
编码阶段另交付生产 `compose.oa.yml` 与固定版本镜像，服务名称统一为hyperf/mysql/redis/edge。
生产Compose应通过配置检查，不能将已有MySQL5.7卷直接挂载到MySQL8；如有既存数据，先做独立导入验证和备份。

## 2. 配置清单

服务端runtime env每个变量独占一行，由部署秘密配置提供，以下占位符须替换，禁止提交真实值：

```dotenv
APP_NAME=MineOA
APP_ENV=prod
APP_DEBUG=false
APP_URL=https://api.example.com
DB_HOST=mysql
DB_PORT=3306
DB_DATABASE=mineoa
DB_USERNAME=mineoa
DB_PASSWORD=REPLACE_WITH_DB_SECRET
REDIS_HOST=redis
REDIS_PORT=6379
JWT_SECRET=REPLACE_WITH_BASE64_DEFAULT_SECRET
JWT_TTL=3600
JWT_REFRESH_TTL=7200
JWT_BLACKLIST_TTL=7201
JWT_MOBILE_SECRET=REPLACE_WITH_INDEPENDENT_BASE64_SECRET
JWT_MOBILE_TTL=43200
JWT_MOBILE_REFRESH_TTL=2592000
JWT_MOBILE_BLACKLIST_TTL=2592001
WX_MINI_APPID=REPLACE_WITH_APPID
WX_MINI_SECRET=REPLACE_WITH_SECRET
WX_SUBSCRIBE_TEMPLATE_APPROVAL_TODO=REPLACE_IN_PHASE3
SMS_ACCESS_KEY_ID=REPLACE_WITH_KEY_ID
SMS_ACCESS_KEY_SECRET=REPLACE_WITH_SECRET
SMS_SIGN_NAME=REPLACE_WITH_APPROVED_SIGN
SMS_TEMPLATE_LOGIN=REPLACE_WITH_APPROVED_TEMPLATE
```

密钥各自独立生成，配置到 `jwt.php` 顶层default/mobile，mobile黑名单前缀独立。
会话撤销与rotation以MySQL为准；实际token有效秒数受首次登录后30天硬上限约束。
Redis清空不能恢复已经退出的mobile会话。服务器时区Asia/Shanghai，主机时钟同步。

web生产配置：VITE_APP_ROOT_BASE=/，VITE_OPEN_PROXY=false，VITE_APP_API_BASEURL=https://api.example.com。
mobile生产配置：VITE_APP_PUBLIC_BASE=/、VITE_SERVER_BASEURL=https://api.example.com、
VITE_APP_PROXY_ENABLE=false、VITE_AUTH_MODE=double，微信三环境基址按实际发布环境设置。
这些前端变量均为构建期输入；修改后重新构建静态产物，不能只重启Nginx。
前端构建产物不得包含AppSecret、JWT密钥或短信凭据。

## 3. 固定URL映射与生产产物

| 域名/路径 | 目标 | 配置要求 |
| --- | --- | --- |
| https://admin.example.com/* | web静态产物 | base=/，history回退/index.html，静态资源404不回退HTML |
| https://m.example.com/* | mobile H5产物 | base=/，SPA回退/index.html |
| https://api.example.com/admin/* | Hyperf9501 | 原路径反代，含passport及OA；不能分配给静态站点 |
| https://api.example.com/api/v1/oa/* | Hyperf9501 | 原路径反代，移动认证与业务 |
| https://api.example.com/health | 待实现健康探活 | 返回基础存活，不暴露连接信息 |
| /uploads | 只允许既有公开附件策略需要的独立公开目录 | 不映射private_oa及预览缓存 |

edge镜像包含web/H5产物及三个server配置。API上游示意（应由生产Nginx配置落实）：

```nginx
upstream oa_backend { server hyperf:9501; }
# api.example.com 对应的TLS server内；证书与通用TLS配置由部署配置提供。
location /admin/ { proxy_pass http://oa_backend; }
location /api/v1/oa/ { proxy_pass http://oa_backend; }
location = /health { proxy_pass http://oa_backend; }
```

反代统一转发Host/X-Real-IP/X-Forwarded-For/X-Forwarded-Proto，只信任实际代理网段。
CORS只放行admin.example.com与m.example.com，支持Authorization、Content-Type、Accept-Language及必要请求ID头，
OPTIONS返回正确允许方法；由Nginx与应用二者之一统一处理，避免重复冲突。Bearer认证不启用跨站Cookie。
微信request/uploadFile/downloadFile合法域名配置 `https://api.example.com`，不含业务路径；HTTPS证书与备案按实际平台要求准备。

生产Compose交付契约：hyperf镜像工作目录/opt/www，命令php bin/hyperf.php start；
环境来自受控runtime env，数据/附件/日志命名卷持久化；edge镜像同版本包含静态文件与代理配置。
hyperf/mysql/redis无宿主公开端口；edge暴露443。镜像、扩展与依赖在构建期安装，运行期不拉取最新代码。
单据附件一阶段就需要private_oa；三阶段增加目录权限，Office转换后续启用。

首次全新部署先启动mysql/redis，完成一次mine:install，再执行OA迁移及幂等oa:seed。
办公主部门与角色/策略初始清单经人工核对；OA种子不得重置密码或批量修改已有user_type。

## 4. 构建、发布与回退

### 4.1 构建产物（实现后的流水线）

| 目录 | 命令 | 产物 |
| --- | --- | --- |
| MineAdmin | composer install --no-dev --optimize-autoloader | 固定composer.lock后端镜像；生产只使用已审查依赖 |
| MineAdmin/web | pnpm install --frozen-lockfile；pnpm build | web/dist，合入edge镜像 |
| MineAdmin/mobile | pnpm install --frozen-lockfile；pnpm build:h5 | mobile/dist/build/h5，合入edge镜像 |
| MineAdmin/mobile | pnpm build:mp-weixin | mobile/dist/build/mp-weixin，体验版验证后上传审核 |

发布清单保存Git提交、后端/edge镜像不可变标识、前端构建配置版本、迁移列表和小程序版本。
不要在运行中的代码目录git pull覆盖文件，也不要把HTTP Worker reload等同于完整应用更新。

### 4.2 增量发布命令模板

前提：生产compose.oa.yml已按§3交付；发布文件.release.env.next包含OA_BACKEND_IMAGE/OA_EDGE_IMAGE等
不可变镜像引用，Compose确实使用这两个变量；runtime凭据由独立受控文件提供。
以下在MineAdmin目录执行，第一次部署不执行备份旧发布文件步骤；新迁移必须兼容当前旧版本。

```bash
docker compose --env-file .release.env.next -f compose.oa.yml config --quiet
docker compose --env-file .release.env.next -f compose.oa.yml pull hyperf edge
docker compose --env-file .release.env.next -f compose.oa.yml run --rm --no-deps hyperf php bin/hyperf.php migrate --force
docker compose --env-file .release.env.next -f compose.oa.yml run --rm --no-deps hyperf php bin/hyperf.php oa:seed
cp .release.env .release.env.previous
cp .release.env.next .release.env
docker compose --env-file .release.env -f compose.oa.yml up -d --force-recreate hyperf edge
docker compose --env-file .release.env -f compose.oa.yml exec -T hyperf php bin/hyperf.php oa:smoke
curl --fail --silent --show-error https://api.example.com/health
```

oa:seed为待实现的幂等OA专用命令，显式调用OA种子；不无差别重跑框架所有Seeder。
迁移只新增/兼容扩展；更新失败时由发布流程停止后续步骤并进入人工/流水线回退，不能忽略失败退出码。
重新创建hyperf确保HTTP Worker、Crontab与OA用户进程均加载同一版本和配置；等待在途任务停机宽限期，
未完成任务由租约恢复。选择非高峰窗口，说明单机短暂不可用，不宣称零停机。

### 4.3 回退到上一固定产物

```bash
docker compose --env-file .release.env.previous -f compose.oa.yml up -d --force-recreate hyperf edge
docker compose --env-file .release.env.previous -f compose.oa.yml exec -T hyperf php bin/hyperf.php oa:smoke
curl --fail --silent --show-error https://api.example.com/health
cp .release.env.previous .release.env
```

不存在docker compose rollback命令。回退使用上一镜像及其配套静态产物，不自动回滚生产业务数据库。
先确认旧版本兼容已执行迁移；破坏性收缩安排单独维护窗口。小程序客户端需服务端至少保留上一客户端契约。
只有冒烟通过才更新“当前发布成功”记录；失败保留完整版本与日志供排查。

## 5. 后台任务与可靠恢复

| 任务 | 计划 | 关键条件 |
| --- | --- | --- |
| OA消费进程 | 常驻短轮询，空闲退避 | 从MySQL领取READY且next_retry_at<=now；owner_token+lease_until |
| 租约补偿 | 每分钟 | 恢复过期PROCESSING；检查DONE收据，不重做已提交副作用 |
| 失败重试 | 首次+最多3次 | 间隔1/5/30min，总4次；最终DEAD告警、人工有痕重投 |
| 节点提醒 | 每日 | 7/30天门槛，业务去重键避免重复提醒 |
| 考勤日结 | 每日00:30（二阶段） | 按工作日的主部门/规则区间首次冻结；后续重算沿用快照 |
| 公告发布 | 每分钟（三阶段） | 仅计划发布且到时的记录 |
| 外部推送 | 独立目标任务（三阶段） | 明确成功/失败/UNKNOWN；不把UNKNOWN盲目重试 |

任务注册在Hyperf进程和Crontab配置中，发布完整重启。数据库备份另用独立运维调度，避免应用不可用时连备份也停止。
恢复Redis后从MySQL恢复未确认delivery并重建缓存；恢复数据库后先暂停消费，核对事件与收据的一致点，再恢复任务。

## 6. 备份与文件保护

MySQL每日全量+按实际RPO启用binlog归档，备份异机存储，初始全量保留7天；文件存储及私有PDF单独备份。
备份使用受保护的客户端凭据文件，不把明文密码写入命令或日志。每日检查可读性、大小及恢复元数据；每季度隔离恢复演练。
会话撤销、Outbox、delivery、单据和文件元数据必须在恢复策略中；Redis缓存可重建，不能笼统认为所有业务队列均可丢弃。
private_oa不映射公开静态目录，下载均经业务授权流式交付；数据权限变化在下一次下载请求立即重新判断。

## 7. 监控与告警

| 指标 | 初始告警阈值 |
| --- | --- |
| 核心接口P95 | >500ms持续5min；记录测试数据规模与连接池等待 |
| 错误率 | >1%持续5min |
| 消费READY及最老年龄 | >100条或最老>5min；业务正常延迟后校准 |
| DEAD / UNKNOWN | 新增即通知人工处置 |
| 消费心跳/过期租约 | 连续缺失或持续积压 |
| 日结/备份结果 | 失败即告警 |
| 进程/内存/磁盘 | 结合容器RSS、Worker趋势、可用磁盘；不只依赖memory_limit |

探活与告警通过独立外部拨测/邮件通道，站内信仅辅助；应用故障时不依赖自身站内消息完成告警。
日志按天轮转，保留期先设30天并按企业制度确认；日志带trace/user/instance/event/consumer/耗时，无凭据。
