# MineOA 架构与设计审计报告（D9）

> 日期：2026-10-26
> 整改状态：D1–D8已按A01–A16修订为v0.5；详见D5整改矩阵。以下原审计结论与行号对应整改前版本，保留用于追溯，不能当作修订后文档的现状。
> 范围：D1–D8 当前工作区版本；MineAdmin 后端、web、mobile 及相关依赖源码。
> 基线：composer.lock 中 MineAdmin 组件 v3.2.0；web/package.json 3.2.1；mobile/package.json unibest 4.4.1。
> 方法：设计文档与当前源码静态交叉核对，并通过 Context7 查阅 MineAdmin 3.2、unibest 项目资料。版本细节以本仓库实际源码为准。

## 1. 原审计结论（整改前）

**总体架构方向兼容，但当前设计不能判定为“完全符合 MineAdmin 3.2 与 unibest 约定”，也不宜直接作为已冻结的实施契约。**

后端四层结构、主工程内按层组织 OA、管理端模块目录、移动端技术选型均可保留。主要问题是：部分“已从源码核实”的结论与实际依赖实现不符，认证与接口契约没有闭合，可靠投递、历史数据和部署设计还缺少必要细节。

本报告评估的是设计的可实施性，不是已完成 OA 的运行验收。在 app、databases、tests、web/src、mobile/src 中未检出所规划的 OA 业务实现；因此，文档中的锁、Outbox、数据权限和性能目标均不能视为已经验证。

| 维度 | 判定 | 说明 |
| --- | --- | --- |
| MineAdmin 后端分层 | 基本符合 | Controller → Service → Repository → Model；OA 放各层子目录可行，无须强制插件化 |
| MineAdmin 版本基线 | 基本符合 | 组件锁定 v3.2.0；需记录当前项目补丁与上游版本的差异 |
| 路由、权限、响应约定 | 部分符合 | D2 部分描述正确，D4 仍保留冲突写法；独立错误码枚举不能直接传给现有 Result |
| 移动端认证接入 | 未闭合 | JWT 场景配置位置错误，双 token、刷新、用户信息、退出接口未统一 |
| unibest 工程约定 | 部分符合 | 版本、Vue/TS/UnoCSS/Pinia 等匹配；主请求链、store、页面配置和分包设计需修订 |
| 审批业务建模 | 部分符合 | 状态机、单据分离、快照方向合理；抄送及多轮历史不完整 |
| 可靠投递与考勤历史 | 待补设计 | 缺少持久化消费去重、确认协议、规则和部门历史口径 |
| 部署与验收 | 未闭合 | 静态与接口路径冲突，迁移发现和发布回滚流程存在问题 |

优先级定义：P1 为对应模块实施或发布前必须解决的问题；P2 为影响一致性、维护或后续交付的明确缺口。三阶段事项不必阻塞一阶段，但应保留为未关闭项。

## 2. P1 问题

### A01：JWT 场景配置位置与依赖实现不符

- **设计依据**：D2:148–155、D5:L1、D7:33 均要求在 `jwt.php` 的 `application` 节点下新增 mobile。
- **源码证据**：`MineAdmin/vendor/mineadmin/jwt/Factory.php:34` 的 `getConfig()` 通过 `getConfigKey($scene)` 读取场景，`getConfigKey():45` 返回 `jwt.<场景名>`。`config/autoload/jwt.php:46` 虽有 application 空节点，但当前 Factory 不读取其子节点。
- **影响**：只添加 `jwt.application.mobile` 不能让 `get('mobile')` 取得设计中的独立密钥和 TTL，文档承诺的场景隔离配置不能据此成立。
- **修订**：按已安装 Factory 的实际配置契约，明确 `jwt.mobile` 与 `jwt.default` 的合并关系；同步 D2/D5/D7。`get('api')` 的调用存在，不等于已有一套独立 api 场景参数。重新打开 D5 L1 的 JWT 核对项。

### A02：双 token 登录与接口路由契约未闭合

- **设计依据**：D2:180 要求 access/refresh 双 token；D4:41、48 却只返回 `token`。D4 使用 `/api/auth/*`，D8:81 使用 `/api/v1/auth/*`，D8:82、91 又使用 `/api/v1/oa/auth/bind`、`me`，后两者没有对应 D4 契约。
- **源码证据**：`MineAdmin/app/Service/PassportService.php:61` 返回 `access_token`、`refresh_token`、`expire_at`，其中 expire_at 当前实际是有效秒数。`mobile/src/api/types/login.ts:11` 期望 `accessToken/refreshToken/accessExpiresIn/refreshExpiresIn`；`mobile/src/api/login.ts:32` 刷新请求还使用另一组路径与 body 字段。
- **影响**：登录成功不代表 store 能保存正确的 token 和过期信息；刷新、恢复用户信息、退出及绑定页面没有一致的后端接口。
- **修订**：在 D4 冻结唯一认证前缀及 login/wechat-login/bind/refresh/me/logout 清单，明确刷新 token 的传递位置、字段名、有效期单位和失败响应；在移动端 API 边界做一次字段适配。不要让页面分别猜测三套契约。

### A03：移动端实际主请求链与设计不一致，登录拦截尚未落实

- **设计依据**：D2:178、D8:70、101 将 alova 作为当前请求主链；D8:100 将 token 管理放进 useUserStore；D8:102 宣称维护登录白名单。
- **源码证据**：`mobile/src/api/login.ts:2` 引入 `@/http/http`，`src/main.ts:3` 注册 `http/interceptor`；`hermes/api.md:3`、`hermes/architecture.md` 明确 uni.request 为主、alova 为可选。`src/http/alova.ts:28` 刷新处理仍为空占位，`:63` 的 token 也是占位字符串。当前凭据由 `src/store/token.ts` 管理，`env/.env:41` 仍为 single。`src/router/interceptor.ts:14` 的 invoke 当前执行路径归一化和 tabbar 角色处理，没有设计所述登录白名单判断。
- **影响**：直接按 D8 开发会绕过现有请求规范，重复建设认证逻辑；“模板已有登录拦截”不能作为 OA 接入已完成的证据。
- **修订**：建议沿用当前 `src/api → http.ts → interceptor → uni.request`，配置 double 并适配 MineAdmin 契约；token 留在 useTokenStore，用户资料留在 useUserStore。若决定迁移 alova，须另写迁移方案并统一登录、刷新、上传和错误处理。补齐普通页面登录门禁、H5 直接进入和小程序启动入口设计。

### A04：员工在后台完成审批的身份路径没有设计

- **设计依据**：D2:160 将 OA 员工定义为 USER(200)；D1:143 和 D8:57 要求后台可发起、处理审批。
- **源码证据**：`app/Http/Admin/Controller/PassportController.php:67` 登录固定传 `Type::SYSTEM`；`app/Service/PassportService.php:49` 按用户类别查账号。该 Service 是 final，`:38` 的场景是私有 default；D2:34 所述优先继承不适用于该具体类，CurrentUser 的刷新调用也指向此 Service。
- **影响**：不能仅增加 OA 菜单，就认为 USER(200) 员工可通过现有后台登录和审批。用户类别、业务角色、终端和 JWT 场景的关系仍不清晰。
- **修订**：增加员工 PC 登录与授权矩阵，明确是否使用独立员工 PC 入口，或对现有认证做受控扩展；mobile 认证服务及刷新/退出使用显式场景依赖。避免通过修改单例中的可变场景字段切换请求身份。

### A05：路由注解与错误码适配方案存在相互冲突的实施指令

- **设计依据**：D2:94 正确描述 Swagger 完整路径，但目录树:42 仍写 Controller(prefix)；D4:21、181 写 `#[Auth]`，:186 写 AutoController。D2:103、D4:28 指向 `App\BusinessException`，D2:104 又写复数 Exceptions。D2:101 允许独立 OaResultCode 直接经 Result 输出。
- **源码证据**：`app/Http/Admin/Controller/Permission/DepartmentController.php:36` 使用 HyperfServer、显式三个中间件及方法级 `Permission(code: ...)`；`:47` 使用完整路径。实际异常是 `App\Exception\BusinessException`。其构造器:22 和 `Http/Common/Result.php:29` 都强类型要求官方 ResultCode。
- **影响**：照不同章节实现会得到不同路由和权限链；独立 OA 枚举不能直接替代该参数。错误码“公式”与 110001 等示例也没有形成统一编码规则。
- **修订**：统一控制器样板、Admin Request 目录、命名空间及中间件要求。错误响应明确选择受控扩展官方枚举，或新增 OA 异常/响应适配层及处理器；同时区分 HTTP 状态与 JSON 业务码。将涉及核心文件的修改列入 core-patch 清单。

### A06：数据权限只规划了列名，没有完整落实框架接入契约

- **设计依据**：D2:320–332、D4:182 主要说明 deptColumn/createdByColumn，HR 默认 DEPT_TREE；D8 也将其作为已确定实现。
- **源码证据**：`app/Library/DataPermission/Attribute/DataScope.php:21` 的 scopeType 是 `ScopeType`；部门树是 `Model/Enums/DataPermission/PolicyType.php:21` 中的 `PolicyType::DeptTree`，两者职责不同。`DataPermission/Aspects/DataScopeAspect.php:78` 的表范围处理依赖 onlyTables，且读取 `CurrentUser::ctxUser()`。`CurrentUser.php:41` 的用户加载才写入 current_user 上下文。
- **影响**：仅写“挂注解”不足以保证按设计过滤；日结表只有 user_id，没有默认 created_by，仍需为该表明确 scopeType 和列映射。异步导出也不能自动继承 HTTP 上下文。
- **修订**：逐个资源声明 onlyTables、列映射、ScopeType、PolicyType、用户上下文初始化与策略分配方式；导出任务保存可信操作者及授权范围，并在执行时明确权限口径。将功能权限、数据范围和资源归属三类检查分别设计。

### A07：OA 迁移和种子子目录不会自动被现有扫描递归发现

- **设计依据**：D2:86–87、363 规划 migrations/oa 与 seeders/oa；D7:81 预期普通 migrate 后即可执行 OA 迁移。
- **源码证据**：`vendor/mineadmin/core/Subscriber/BootApplicationSubscriber.php:42` 注册 databases/migrations、databases/seeders；Hyperf `Migrations/Migrator.php:176` 使用当前目录 `/*_*.php`，`Seeders/Seed.php:158` 使用 `/*.php`，均不递归扫描 OA 子目录。
- **影响**：不补路径注册或显式路径命令，OA 文件可能不在默认发布迁移集合中；有“建表设计”不等于部署会建出表。
- **修订**：优先在现有 databases/migrations 和 databases/seeders 根目录以 OA 文件名区分；若保留子目录，写出路径注册、migrate/seed/status 的明确命令及顺序。同步 D2/D7，不以笼统的“独立分组”代替加载设计。

### A08：Outbox 的队列确认与消费去重没有持久化设计

- **设计依据**：D2:138、D3:343–359 要求可靠最终副作用，D7:140 认为 Redis 数据可丢。D3 的消息表没有来源 event_id 或对应唯一约束。
- **缺口**：事件已写 Redis、生产端已标记 delivered，不等于消费者已经提交数据库副作用。文档没有说明消费者确认、Redis 恢复后重投、各消费者独立去重和并发领取方式。next_retry_at 可为 NULL，而 D7:121 的扫描条件只写 `<=now`。
- **影响**：现有文字尚不足以支持“提交成功则最终发生”的保证；只说按 event_id 幂等，没有明确去重记录与副作用的同事务边界。
- **修订**：明确至少一次投递语义、领取租约、超时恢复、重试/死信/人工重投和空重试时间语义；业务消费者采用持久化去重记录，与副作用同事务提交。消息可使用事件与接收人唯一键。定义 delivered 与 processed 的区别，并给出 Redis 丢失后的恢复策略。

### A09：考勤规则的 JSON 索引和历史重算口径不完整

- **设计依据**：D3:218 的 dept_scope 是 JSON，但:221 设计 `idx_effective(dept_scope(64), effective_date)`。D3:247 使用“结算时所属部门”，D2:207 同时要求历史可重算；D8:59 期望规则改版新增版本。
- **影响**：MySQL 8.0 不能把该 JSON 列按普通字符串前缀索引直接使用。仅 effective_date 和可变 status，不能完整说明规则停用、部门调动后的历史重算；重新取当前部门会改变历史归属。用户本身还是多部门关联（`app/Model/Permission/User.php:152`）。
- **修订**：规则适用部门关系优先拆关联表，或明确经过验证的生成列/JSON 索引方案；规则版本不可覆盖，定义指定日期的选版与停用语义。明确主部门或发起部门的选择、人员调动历史及重算沿用的部门快照。补卡修正还需说明与原始只追加记录及唯一键的关系。

### A10：静态入口与后端 API 的部署路由冲突

- **设计依据**：D2:340、D7:58 把 `/admin` 分配给后台静态产物，但所有后台接口也是 `/admin/*`；拓扑只将 `/api` 反代到 Hyperf。
- **源码证据**：后台登录路径为 `/admin/passport/login`。`web/vite.config.ts:29` 用 VITE_APP_ROOT_BASE，当前 web 生产配置为 `/`；mobile 的 VITE_APP_PUBLIC_BASE 也为 `/`，与设计中的 `/h5` 未对齐。web/src/utils/http.ts 还依赖实际 API baseURL 配置。
- **影响**：按该拓扑直接落地，后台请求、SPA 路由和静态资源的去向不明确；子路径刷新和构建资源地址不能保证正常。
- **修订**：固定一套可执行的 URL 映射。建议后台静态入口与 `/admin/*` API 分离，或采用独立域名；分别列出 web base、router history、API base、H5 base、Nginx try_files/反代和微信合法域名。合法域名不包含 `/api` 路径。

### A11：文档权限缺少私有文件存储与交付设计（三阶段）

- **设计依据**：D3:330 复用 attachment；D4:169–173 要求目录权限校验后下载/预览。
- **源码证据**：`config/autoload/file.php:23` 的默认本地驱动具有 public_url；`app/Model/Attachment.php:29` 具有 url 字段。设计尚未指定 OA 私有附件及转换 PDF 的存储和访问方式。
- **影响**：复用 attachment 元数据不能单独证明底层文件也受 OA 权限控制。当前没有 OA 文件实现，因此此项是设计缺口，不是已经确认的泄露事件。
- **修订**：为受限文件和预览 PDF 明确私有存储、授权下载或短期签名交付、缓存失效及权限变更处理；同时确定附件归属与业务单据关联校验。可继续复用 attachment 元数据。

## 3. P2 问题

### A12：后台页面契约、菜单组件值与分页约定未对齐

证据：D8:57 明写后台流程接口“D4 待补全”；D4 管理端审批只列模板接口。D8:50 指向 `modules/oa/views/...`，而 `web/src/store/modules/useRouteStore.ts:142` 会自行拼接 `../../modules/` 和后缀；菜单表单另有 componentPath。组件值应明确为例如 `oa/views/approval/template/index`，与 componentPath、componentSuffix 分开。D4:13 使用 pageSize，但后台 AbstractController:28 读取 page_size；IRepository:54 默认只输出 list/total。

修订：补齐 admin 流程与员工选择、附件上传、模板编辑所需接口；写出一条完整菜单种子样例及具体权限码，不能只列 `oa:...:*`。冻结后台与移动端各自分页 DTO 或在边界适配，说明 total/list 的映射。D8 中的 DynamicForm 还需明确固定 billData 与 formData 的字段来源。

### A13：抄送、多轮节点和表单值历史仍缺少数据模型

证据：D3:42、D4:76、80 支持动态抄送及“抄送我的”，但数据字典没有实例抄送接收人关系或等价持久化字段。D2:270 要求重置节点并保留任务，D3:96 的节点唯一键只有 instance_id/seq，节点没有 round；D4:84 会更新当前 formData、billData。

修订：增加实际抄送接收人快照和可查询索引；决定节点按轮次实例化，或另存每轮节点历史。明确重新提交后的旧表单值和单据值保存在哪里。表单定义快照不能替代每轮填写值的历史快照。D8:86 的“REJECTED 可重提”还需改为与状态机一致：回退发起人为 DRAFT，终态 REJECTED 默认不可重提。

### A14：unibest 页面设计缺少分包、Tabbar 对应页和配置事实源

证据：D8 将全部 OA 页面放在主 pages，规划四个 Tab，但没有明确 approval Tab 的固定页面路径。`mobile/hermes/performance.md:3` 要求独立低频页面分包；`vite.config.ts` 的 UniPages 已配置 pages-demo；`hermes/architecture.md` 约定页面使用 definePage，tabbar 来自 src/tabbar/config.ts，JSON/d.ts 为生成物。D8:72 却采用“路由块注释”泛指。

修订：主包保留启动、登录和四个固定 Tab 页面；审批详情/表单、考勤二级、公告详情等按依赖与体积拆分业务包，并更新 subPackages。H5 专属文档页面以条件编译隔离。明确 definePage、tabbar/config.ts、pages.config.ts 的职责和包体积验收；wot-design-uni 安装及 easycom 配置是已声明待办，不能算模板已有能力，也不是选型本身不兼容。

### A15：发布命令和构建环境说明不能直接执行

证据：D7:104 使用 `docker compose rollback`，该命令不成立；:96–104 没有完整产物版本切换与前置迁移步骤。D7:27、35 等把多个变量写在同一行，若直接复制为 dotenv 不等价于多行变量。D7:17 只写 Node20+，而本机已安装 web Vite8.3.5 的 engines 要求 `^20.19.0 || >=22.12.0`。文档将 Worker reload 与所有自定义进程及配置重新加载等同，也需要按实际进程模型修订。

修订：提供一变量一行的模板；锁定满足两端工具链的 Node/pnpm 版本；发布使用固定提交或镜像、明确迁移顺序、重新生成容器/代理缓存、进程重启范围和上一产物回退步骤。`/health`、oa:smoke 当前为待实现能力，不能在已有运维能力中标为完成。

### A16：分期验收与测试骨架不一致，D5 关闭状态过于乐观
